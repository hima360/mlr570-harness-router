# Fix the judge before copying anyone's harness

v4 should spend its effort on **when the harness declares a task done**, not on a new framework, more routing or more cache work. Our own dev traces are the strongest evidence in this pack. The Opus judge says "ship" and the verifier agrees **9 of 23 times (39%)**. The judge costs **$10.89, 23% of takeover-era spend**. And the five tasks no setup ever solved ate **40% of dev spend** ([dev traces](../research_notes/Open%20agent%20harnesses%20for%20v4/our_dev_traces.md)). The open-source field agrees on the cure. Every harness that measurably improved forced *executable* verification before exit rather than trusting a model's reading of the trajectory. DeepSeek's harness (`dsh`) is real, MIT-licensed and competitive, but it is not better than its peers. Its headline numbers are self-reported model scores run under mixed harnesses. The one independent same-model board puts it in a statistically tied top group, and it loses Terminal-Bench server tasks by killing background processes on exit. Borrow four small ideas from it, not the framework. For the chat app, a FastAPI server that turns our existing `Trace.log` events into AG-UI events, rendered with assistant-ui (the kit Hermes Desktop uses), gives a Codex-like look in about a week. A replay mode then reads saved traces and never calls a model.

## DeepSeek's harness is good, not exceptional, and not ours to adopt

`dsh` is an official, MIT-licensed TypeScript harness. It was created 2026-08-13 and still ships only release candidates (latest rc.5, 2026-11-18), under a README warning of compatibility-breaking changes ([GitHub](https://github.com/deepseek-ai/deepseek-harness)). The "very good" claim rests on DeepSeek's API changelog. That changelog reports *model* scores and labels the harness inconsistently: "DeepSeek Harness minimal mode" for V4-Flash, nothing stated for V4.1-Flash, and "the Claude Code framework" plus Mini-SWE-V2 for V4.1-Flash-1017 ([DeepSeek updates](https://api-docs.deepseek.com/updates/)). Those numbers say nothing about dsh against other harnesses.

The only fair test swaps harnesses at a fixed model. The HF Harness Leaderboard runs Terminal-Bench 2.1 and DeepSWE through Harbor, with three attempts per task and bootstrap-CI ties. On **GLM-5.3-Flash at high effort, dsh scores 63.5, 5th of 10 and statistically tied with the leader**. Pi scores 65.9 on the same model. The board also reclassified **20 dsh passes as cheating** (fetching reference solutions), and it recorded that dsh's process manager removes background services before the grader calls them ([HF CHANGELOG](https://huggingface.co/spaces/joelniklaus/harness-leaderboard/blob/main/CHANGELOG.md)). A secondary report puts that at 2 of 36 attempts on server tasks where others passed 36 of 36 ([devopschat summary of The New Stack](https://www.devopschat.co/articles/deepseeks-coding-agent-is-too-tidy-for-its-own-good-and-benchmarks-are-punishing-it)). The same board found, per a secondary summary, that **mini-swe-agent was the best harness on GLM-5.3-Flash at launch** ([aicoder](https://aicoder.com/news/news-20261105-joel-niklaus-hf-harness-leaderboard-28849-trials-mini-swe-agent-51-4)). That is a reason to keep our builder loop.

Four things are worth borrowing. The first is dsh's "model-visible means logged" rule: every request must be reconstructable from the session log ([architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)), which the UI and replay mode depend on. The second is pruning oversized tool results before any summarising ([compaction](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/README.md)). The third is declaring each model's context window and maximum output explicitly. dsh's auto-compaction silently switched off when the two were equal ([HF CHANGELOG](https://huggingface.co/spaces/joelniklaus/harness-leaderboard/blob/main/CHANGELOG.md)). The fourth is a pair of anti-patterns to avoid: never kill background processes at exit, and block web access that can reach reference solutions. The framework itself (Cordis plugins, TypeScript, RC-only releases, no multi-model escalation) would cost more to wrap than it returns.

## Executable verification is the one harness change with repeated evidence

Most harness evidence comes from whole-harness swaps, and the Terminal-Bench 2.0 authors conclude that **model choice generally matters more than scaffold** ([arXiv 2601.11868](https://arxiv.org/html/2601.11868)). The interventions that moved scores on a fixed model share one theme. LangChain raised gpt-5.2-codex from **52.8% to 66.5%** on Terminal-Bench 2.0 through harness changes alone. The bundle included a pre-completion checklist that intercepts exit and forces verification against the spec, an environment map at start, loop detection and an effort "sandwich". The authors name the dominant failure as an agent re-reading its own code, judging it fine and stopping ([LangChain](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)). That result is a vendor self-report with only the effort piece isolated. Independently, "false success" is **75.8% of failures** on AppWorld. No LLM-judge configuration was reliable, and judges read longer trajectories as success ([arXiv 2606.09863](https://arxiv.org/abs/2606.09863)). The older SWE-agent ablation is the only clean component study: a lint-on-edit guardrail was worth **+3.0 points** on an 18.0% base ([arXiv 2405.15793](https://arxiv.org/html/2405.15793v3)).

Our data reproduces the failure exactly. The wrong ships are near misses: cargo at 0.70 (x4), mvcc at 0.73, fin-saccr at 0.92. v3.5 and v3.7 shipped fin-saccr at 0.92 and failed, while v2.8 and v2.9 sent it to "fix" and solved it. The judge never runs the task's own checks. It spends a **median of 4 Opus calls per review** exploring, at about 770 output tokens each ([dev traces](../research_notes/Open%20agent%20harnesses%20for%20v4/our_dev_traces.md)). Those exploration calls are where tests could run instead. Swapping them for test output should raise ship precision and cut judge cost together. That is inferred, not measured.

Rank 1 is the only change aimed at solves with direct support from both our data and outside evidence. Ranks 2, 4 and 5 are cost changes that should leave solves flat by construction. Ranks 3, 6 and 7 are cheap hygiene. One risk to rank 1: builder-written tests can encode the same misreading of the spec that produces the plateaus. So the judge must see the spec next to the test output, not the test output alone.

## Where the literature and our traces disagree

Our traces overrule outside advice in four places. First, **cache work is done.** The previous report ranked a stable takeover cache as the top lever, worth up to about 30%. The dev traces show mid-role session breaks disappeared once v3.5 raised the session budget to 300k. Waste beyond cold starts ($4.10 across all runs) is now near zero, so no further cache work is warranted. Second, **dependency pre-baking is not worth building here.** Terminal-Bench's 24.1% missing-executable share suggests caching installs ([2601.11868](https://arxiv.org/html/2601.11868)). Our 42 install commands took **249 s in total**, so the cheap probe in rank 3 is the right size. Third, **loop detection and takeover caps do not fit our failures.** Identical repeated commands occurred only 24 times, and long takeovers are solves (up to 43 calls), so LangChain's loop middleware and a length cap address problems we do not have ([traces](../research_notes/Open%20agent%20harnesses%20for%20v4/our_dev_traces.md)).

Fourth, **sources disagree among themselves on condensing context.** OpenHands reports its summarising condenser as solve-neutral at half the per-turn cost ([OpenHands](https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents)). Other work finds LLM summarisation lengthens trajectories and cost a thinking model 9 points ([arXiv 2508.21433](https://arxiv.org/html/2508.21433v3)). Verbatim truncation (rank 4) avoids the dispute. A fixed-schema handoff summary (goal, progress, failing checks) is the one place a structured summary is still worth testing.

The plateaus deserve a separate warning. cargo sits at 0.70 in 8 of 9 runs, vf2 at 0.98 in 5 of 5 and heat-pump at 0 in 9 of 9, whatever the model, Opus alone included ([traces](../research_notes/Open%20agent%20harnesses%20for%20v4/our_dev_traces.md)). Any v4 change that "fixes" one of these on dev, without moving held-out results, is benchmark tuning. These tasks should be reported, not targeted.

## A thin assistant-ui app over the trace we already write

Every harness event already passes through one method, `Trace.log(event, **data)` in `phase2/trace.py`. The events cover `plan`, `route`, `llm_call`, `escalate`, `takeover`, `senior_review` and `done` ([UI notes](../research_notes/Open%20agent%20harnesses%20for%20v4/agent_ui.md)), so the harness needs no change. A FastAPI endpoint should start a run in the background, push trace rows to a queue and encode them as AG-UI events over SSE using the `ag-ui-protocol` Python package ([AG-UI Python](https://github.com/ag-ui-protocol/ag-ui/tree/main/sdks/python)). The events map directly. `plan` becomes a state snapshot of the DAG. `route` becomes a custom "who is working" badge (model, tier, Laya score). `llm_call` becomes a tool call plus a state delta carrying tokens and cost. `escalate` and `takeover` become badges. `done` finishes the run ([AG-UI events](https://docs.ag-ui.com/concepts/events)). The front end is assistant-ui, MIT-licensed, with AG-UI and custom-server backends ([docs](https://www.assistant-ui.com/docs)). It is the chat layer Hermes Desktop ships on ([package.json](https://github.com/NousResearch/hermes-agent/blob/main/apps/desktop/package.json)). Vercel's Apache-2.0 AI Elements supplies ready Plan, Task, Tool, Context (token meter) and Model-selector components ([AI Elements](https://github.com/vercel/ai-elements/tree/main/packages/elements/src)). Open WebUI is the wrong base: its licence forbids removing its branding above 50 users ([LICENSE](https://github.com/open-webui/open-webui/blob/main/LICENSE)), and its status lines cannot show a step tree. The one-week estimate is ours and unsourced.

Three product rules matter more than the component choice. Estimated cost must be **tokens times the list price in config**, labelled "estimated", never the subscription bill. That is a project rule, and it keeps live and replay numbers comparable. Provider connections belong in a status panel fed by the opencodex model list and each route's last success or failure, so a `ProviderUnavailable` shows before a run silently loses its takeover. Latency should be visible too: GLM builder calls are **44% of all trial time** at a median 9.7 s ([traces](../research_notes/Open%20agent%20harnesses%20for%20v4/our_dev_traces.md)), so a per-step timer is the honest answer to "is it stuck?".

The benchmark replay mode should be a separate route that reads a job's trace JSONL and `result.json` (via the existing `phase2/replay.py`), plays the events back through the same AG-UI encoder and shows the verifier reward at the end. It must never call a model. It must also be labelled as a recording, not a re-run, because swapping models mid-trajectory rewrites 61-94% of later actions, so a replay cannot show what a different route *would* have done ([arXiv 2608.08239](https://arxiv.org/pdf/2608.08239)). One gap remains open: the live chat mode currently runs only inside a Harbor task container. A general product needs a local-workspace environment behind the same `environment.exec` interface, and none of the sources covers that.

## Conclusion

The open-source field contributes less than its star counts suggest. Harness swaps at a fixed model move scores by single digits, and the best-documented gains all come from making the agent prove completion. Our weakest link is the same: an expensive Opus judge that reads instead of runs. That makes v4 a narrow, testable bet. Rank 1 alone should show up as fewer wrong ships on dev at equal or lower judge cost, and it can be red-teamed with the judge and takeover numbers already in hand. Everything else is cheap hygiene or solve-neutral cost mechanics. The UI and replay work can proceed in parallel because they touch only the trace, not the policy.
