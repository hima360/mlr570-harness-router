# Factory Droid (Terminal-Bench #1) — practices for phase2

Sources: factory.com/news/terminal-bench ("TB post"), factory.com/news/model-routing-belongs-in-the-harness ("routing post"), factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks ("PB post"), docs.factory.com (droid-exec, subagents, missions), `droid exec --help`, `~/.factory/droids/scrutiny-feature-reviewer.md` and `user-testing-flow-validator.md`.

## Practices worth copying

**1. Session continuation instead of message replay.** Droid keeps one session and continues it (`-s, --session-id <id>`; "preserves context, no message replay", `droid exec --help`). We re-serialize the whole conversation every call (`phase2/cli_models.py:19 serialize`, `phase2/droid.py:26 complete`), the direct cause of 40k-token prompts. Change: in `phase2/droid.py`, keep a per-worker `session_id` returned by the first call's JSON `result.session_id`, then pass `-s <id>` with only the messages since the last call. The Droid-side history lives in its daemon; our `worker_*.json` trace stays authoritative. **High value / medium effort.**

**2. Mid-conversation "system notifications".** Three-tier prompting; the "system notifications tier proved particularly crucial", injected "at appropriate conversation points" for "rapid error recovery" (TB post). Our format rules appear once in the first prompt (`phase2/worker.py:110 TEXT_FORMAT_HINT`), so weak models forget them. Change: in the model wrapper (`phase2/cli_models.py`, `CliTextModel._query`) and `worker.py`, when a reply parses to zero commands or a turn is dropped by `compact_messages`, inject a short corrective user-role notice at the newest position ("last reply had no `mswea_bash_command` block; resend exactly one"). Same channel serves R4 team updates. **High value / low effort.**

**3. Environment bootstrap shown as command output.** Droid boots each session with "a broad range of salient system information"; presenting it "as shell command output helped Droid avoid redundantly reissuing similar commands" (TB post). Today only the planner sees an env listing (`phase2/orchestrator.py:97 _env_summary`). Change: run one richer probe per run (pwd, ls, `env | sort`, git status, os-release) and paste it into `worker.py INSTANCE_TEMPLATE` as a fake output block before turn 1. **High value / low effort.**

**4. Keep the check behind a wall.** In Factory's best system, the implementer "never authors it, runs it, or sees its cases": "once a sparse sample becomes visible, it becomes the target" (PB post). Our planned context builder would show the worker "the check that will judge it" (design doc, section 2) — that invites teaching-to-the-test and makes format-only passes likelier. Change: in the context builder / `worker.py outputs_hint`, pass the goal and the promised outputs, never the literal `step.check`; keep checks verifier-side only. **High value / low effort.**

**5. Validator from a different model family.** "Our default validator comes from a different model family than our default implementer"; "a useful validator should fail where the model it reviews does not" (routing post). Our check is authored by the planner and greps a value the same worker wrote (`phase2/verifier.py:11`). Change: for fact outputs, have the planner also emit a recompute command (regenerate domains from the seed — already hinted in `planner.py PLANNER_PROMPT`), and in `orchestrator._attempt` run an optional cross-family spot-check: a cheap model on a different backend re-derives the value independently; disagreement forces a retry before escalation. **High value / high effort.**

**6. Show tool runtimes above a threshold.** "Making the LLMs aware of the tool and session run time... runtimes are only added when they exceed certain thresholds" (TB post). Change: in `worker.py HarborEnvAdapter.execute`, append `[ran 143s]` to outputs over a threshold so the model stops repeating slow commands and chooses narrower slices (helps the 180 s stall pattern). **High value / low effort.**

**7. Short default timeouts, fail fast.** "Using short default timeouts led to better average performance by cutting long, unproductive waits" (TB post); the model opts into longer waits explicitly. Our commands inherit one long default (`worker.py` adapter `timeout`), and four 180 s timeouts burned s2 (design doc R7). Change: lower the per-command default in `HarborEnvAdapter` and tell the worker it may prefix long commands with an explicit timeout request. **High value / low effort.**

**8. Plan reminder at the newest end of context.** Crossing off the done step "while simultaneously marking the next item as in progress, inserts an explicit reminder... at the very end/newest section of the context window" (TB post; recency bias is their documented motivation). Our compaction pins the first prompt at the head and folds everything else (`phase2/worker.py:223 compact_messages`). Change: append a final user-role line per call: step goal, what remains, and the submit command verbatim. **High value / low effort.**

**9. Per-model scaffolding.** "Model-specific architectures": one provider's model wants FIND_AND_REPLACE, another V4A diffs; "model-specific tool scaffolding when behavioral differences warranted it" (TB post). Our one-size `PROMPT_HEADER` (`cli_models.py:14`) plus a single format hint is exactly the uniformity they reject; GLM/Flash format errors are our known pain. Change: per-model format scaffold in `cli_models.py` — for weak tiers include a filled-in example turn (THOUGHT + one command block) and drop it for strong tiers. **Medium value / medium effort.**

**10. Cap output tokens and pin reasoning effort per tier.** Droid's custom-model config sets `"maxOutputTokens": 16384` and exec exposes `-r, --reasoning-effort` "defaults per model" (droid-exec docs, `--help`). Our 16k-token replies and timeout stalls are output-side. Change: in `phase2/droid.py complete()` bind `-r` for every tier (today only "low" effort steps), and set a `max_tokens` cap for opencodex models in `phase2/llm.py` so cheap tiers cannot write 16k-token replies. **High value / low effort.**

**11. Never trust the agent's word.** "Exit 0 means Droid finished, not that the task succeeded. Check the result with your own tools" (droid-exec docs). Our verifier still passes a step with no check if the worker submitted (`phase2/verifier.py:12`). Change: make a missing/empty check a plan-repair error in `planner.parse_plan` (a check is already required since 8cadb43) and remove the trust path; TUI line T1 then simplifies. **High value / low effort.**

**12. Fresh-context workers, one return value, explicit "blocked".** Subagents run in a "fresh context window", get a spec "instead of the full session history", return a single message, "cannot spawn subagents", and "report back instead of prompting" (subagents.md, routing post). Validators distinguish `pass/fail/blocked/skipped` (`user-testing-flow-validator.md`). This validates R2 (outputs.txt) and R6 (digest handoff). Change: add `blocked` as a worker exit status distinct from failure (worker publishes `blocker=` today, `worker.py outputs_hint`), and let `orchestrator.py parse_fix` map `blocked` to `rerun_dependency` without burning a retry on the same model. **Medium value / low effort.**

## Do NOT copy

- **Autonomy/permission tiers.** Factory itself ran Terminal-Bench "with all permissions skipped (as the environment was sandboxed)" (TB post). Our containers are the sandbox; per-command policy parsing adds latency and new failure modes for zero safety gain.
- **Mid-session model switching.** A cache-blind switch "exceeds an all-frontier baseline... 2.37 times at turns 151-200" (routing post). We are stateless, so every call is already fresh-rate; switching models mid-step would only add format churn. Switch tiers at step/attempt boundaries only — our current design is right.
- **Mission-scale validation cadence.** The PB system spent "14 times the credits" (216M→3B) for 36%→90% parity, plus per-milestone scrutiny and user-testing passes. Right for parity research; wrong for a cost-focused router paper. One check per step, one repair turn, one escalation.
- **Multi-model for its own sake.** "Our single-model configurations surpass... multi-model agents' performance" (TB post). Routing should pick the cheapest capable model per step, not mix models within a step.
- **Skills/plugins/MCP ecosystem.** Irrelevant to a benchmark harness; keep `droid.py`'s `--disable-builtin-skills --only-tools TodoWrite` so Droid behaves as a stateless model, not an agent on the host.
